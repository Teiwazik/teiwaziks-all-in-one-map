# megamap: design

megamap is a Horizon native mixin mod (`docs/native-mods.md`): one support module plus one injection per hook
point, the format horizon-mixins 0.6 builds (an earlier `[api] path = "api"` trait-mod build was refused there
with E_MANIFEST). One mod gives you a HUD
minimap, a fullscreen world map and waypoints. The code and art are original. The look follows the reference
screenshots in `reference/`: a Xaero-like square or round minimap with info lines under it, and a dark fullscreen
map with a toolbar.

Pinned to Horizon `06ac31ccde2ac174eabdcb0fe82f5109f57f5315`, Mixins `5a64af938ec86b00d53d16a408aabc0038fb3e57`,
game 26.3, native hooks API 455.

## Layout

```
horizon-native.json            native manifest (id megamap)
horizon-mod.toml               content manifest (id megamap): api 0.2, side client, assets only
assets/megamap/textures/gui/   procedural PNGs (tools/gen_art.py)
src/glue.rs                    glue: state, worker thread, drawing, input, commands, hook entry points
src/engine/*.rs                everything that does not touch Horizon (tested on its own)
mixins/megamap/                the bundle (what the .hnmod carries)
  horizon-mixin.toml           mod, compatibility.horizon_revision, 1 module, 19 injections (inline tables)
  runtime.rs                   GENERATED by tools/pack.py: glue.rs with engine/ inlined as `mod engine { ... }`
  frame.rs, hud.rs, key.rs ... one helper per hook point (HEAD injections)
engine-tests/                  cargo test + examples/bench.rs; includes src/engine/ by #[path]
patches/far-surface-accessor.patch   optional 1-function Horizon patch: full LOD surface (water, biome)
tools/gen_art.py, tools/pack.py
```

### The engine/glue split

`engine/` has no Horizon types in it. It sees the game through three small traits:

- `ChunkSource`: block state, biome and height per column, implemented over `NativeClientChunks`.
- `Tints`: grass, foliage and water colours, implemented over `NativeClientBiomes`.
- `Lookup`: block-state facts, such as map colour, fluid or plant, from a table built on the game thread.

Because of this, everything heavy (baking, encoding, mips, composition, UI hit-testing, waypoint storage, trail,
fog, radar) runs in `cargo test` and the benchmark without building the game. `glue.rs` is about 2400 lines. It
converts events into engine calls and engine output into `HudBatch`, `WorldPrimitives` and mod-image uploads.

## Data flow

```
game thread (frame hook)                      worker thread "megamap-baker"
------------------------                      ------------------------------
every 500 ms: client_chunks(area) snapshot -> Job::Bake{snapshot, chunks, epoch}
  (surface +-32 chunks, cave +-8)                bake each chunk -> 16x16 px + heights
client_chunks_changed(prev) picks dirty ones     <- Out::Baked
receive(): integrate <= 64 chunks/frame
  into Region (512x512) and mark dirty
prepare(): visible regions; missing ->       -> Job::Load(path) -> decode MMR1
                                                <- Out::Loaded
evict LRU / on leave                         -> Job::Save(encoded) (region encoded on the worker)
render_minimap / render_world:
  engine::view composes from region pixels
  (mip by zoom) into a reused buffer;
  upload to the mod image only when the
  view key (pos, yaw, zoom, epoch) changed
```

- **Off-thread and time-sliced.** One worker owns all baking, encoding and decoding. The game thread does a few
  cheap things:
  - takes a snapshot, which shares the chunks and does not copy them
  - integrates at most 64 baked chunks per frame
  - builds the block-state table 8192 ids per frame
  - samples the far grid one slice per frame
- **Epochs.** There are two `Arc<AtomicU64>` epochs, one for the surface layer and one for the cave layer. The
  game thread bumps them on a dimension change, a biome-table change (`client_biomes_changed`) or a mode change.
  The worker drops stale jobs and the game thread drops stale results, so a world switch never paints old pixels.
- **Region tiles and the disk format.** A region is 512x512 blocks (32x32 chunks), stored at
  `<data_dir>/<world key>/<dimension>/r.<rx>.<rz>.mmr`. The format, `MMR1` (`engine/region.rs`):
  - an RGB palette with run-length pixel indices
  - heights stored as zigzag deltas, with zero runs collapsed
  - explored-chunk bits
  - an FNV-1a checksum; a corrupt file is ignored and baked again

  A full region is 273 KB on disk against 1.5 MB raw.
- **Mips.** Each region builds mip levels lazily (256, 128 and 64 pixels, and so on) the first time a zoomed-out
  view samples it, and rebuilds them only when it is dirty. A zoomed-out world map samples a mip, not 512² pixels.
- **GPU upload only on change.** Both maps share the mod's one 1024² image (see API gaps).
  - The minimap image is 2S pixels for an S-pixel minimap, for crispness under GUI scale. It is re-uploaded only
    when its view key changes, at most 30 Hz.
  - The world map is uploaded only when pan, zoom, epoch or a dirty region in view changes.
  - Opacity is applied at composition time. There is no tint API, so this is the only place it can go.
- **Rotation is a transform.** `view::compose` samples through an inverse rotation and scale, and applies the round
  mask in the same pass. Turning never re-bakes a chunk. With no rotated textured quad in the API, the transform
  runs on the CPU: 138 us for a 128 px minimap and 526 us for 256 px (bench).
- **Culling.**
  - Only regions intersecting the view rectangle are touched.
  - Waypoint beams are drawn within 256 blocks; farther waypoints get only a label, pulled to 48 blocks so it stays
    readable.
  - Trail segments are cut to the newest 300 on the minimap.
  - Off-map waypoints on the minimap snap to the edge.
- **No per-frame allocations in hot paths.** Composition writes into buffers kept on `State` (`ensure_buf`). The
  bake scratch arrays live on the worker. Info lines reuse `String`s. The one exception is world-primitive text:
  `WorldPrimitives::text` takes `impl Into<String>`, so each visible label costs one `String` per frame. This is an
  API gap.

### Benchmark (engine-tests/examples/bench.rs, release, this machine, v0.3.0)

| step | time |
|---|---|
| bake one chunk (16x16, surface, biome blend, per-block noise) | 55.6 us |
| encode / decode a full region (MMR1, worker) | 3.86 ms / 2.16 ms |
| build mips of a region | 1.50 ms |
| minimap 128 px, rotated, round | 0.32 ms |
| minimap 256 px, rotated | 1.27 ms |
| world map 1024x576, default style (relief 2: hillshade + shadow + AO + water) | 13.8 ms (only on change) |
| world map 1024x576, relief 3 + contours + grid + night | 28.5 ms (only on change) |
| clouds 1024x576 mostly fog, Fast / Normal / Fine / Volumetric: node update | 1.5 / 3.5 / 8.7 / 15.5 ms |
| clouds 1024x576, Normal, Nether / End looks: node update | 3.3 / 3.1 ms |
| clouds 1024x576: composite | 2.0 - 4.0 ms |
| clouds minimap 256x256, Normal (update + composite) | 1.5 ms |

A cloud frame runs only at the cloud FPS limit (by default the map's own rate, capped in Options), not every game
frame; at a 30 Hz limit and Normal quality the world map spends about 5.6 ms every 33 ms on the game thread. The map base
image is rendered once per view change and copied under the clouds, so cloud ticks do not re-run relief.
The cloud node grid and the base copy are reused buffers; nothing allocates per tick after the first frame.

Size on disk: a full region is about 450 KB with v2 detail (noise defeats some of the palette runs), against
1.5 MB raw.

## Packaging: one module, nineteen injections

`horizon-mixin.toml` follows the shipped mixin mods (minimap, zoom, smartf3, shulker_peek, mod_menu):

- `[[module]]` `runtime`: `runtime.rs` becomes `mod native_megamap` in `crates/horizon-client/src/game.rs`.
  horizon-mixins wants a self-contained module (no file attributes, no `mod x;`, `#[path]` or `include!`), so
  `tools/pack.py` inlines `src/engine/*.rs` into it and checks those rules, and `unsafe` (horizon-client is
  `#![forbid(unsafe_code)]`).
- `[[injection]]`: HEAD of each `native_hooks::Game::native_*` hook point, by `target` like the samples:
  frame, client_level_load, client_disconnecting, hud, key, commands, command, client_chat_received, mods,
  settings, settings_click, screen_render_post, screen_mouse_button_pressed/released/dragged/scrolled_pre,
  screen_key_pressed_pre, screen_char_typed_pre, world_primitives. Each helper is one `fn` whose bindings are
  `game` (`&mut *self` or `&*self`) and the hook's own arguments; it calls `crate::game::native_megamap::<entry>`.
- The glue keeps reading the game through `&mut dyn Host` / `&dyn Host`: `Game` implements `Host`
  (generated `game/mod_api_host.rs`), so the helpers pass `game` straight in. State is one
  `static OnceLock<Mutex<State>>` instead of the trait mod's `Box<dyn Hooks>`.
- Options > Mods: a mixin mod is compiled in, so each helper checks `game.native_on("megamap")` first; off means
  no drawing, no keys, no commands, and screen events pass through. `mods`, `settings` and `settings_click` are
  not gated, so the mod stays listed and can be turned back on.
- Screen hooks: the entry returns true when megamap took the event, and the helper sets `*canceled = true`
  (skipped when an earlier mod already cancelled). `command` likewise sets `*ran`.
- The pin stays `7c30002c...`; the RT build's `stage_native_api.py prepare` re-pins it to its tree.

## Hooks used (all documented in `docs/native-mods.md` at the pinned rev)

- **Lifecycle:** `frame`, `client_level_load` (the world and dimension key), `client_disconnecting` (saves
  synchronously: waypoints, trail, settings and dirty regions).
- **HUD:** `hud`, with the minimap in the configured corner via `Corners::place`. The info lines are coordinates,
  biome, time and light.
- **World render pass:** `world_primitives`, the documented in-world draw pass. It draws beams, labels with
  distance (`through_walls`, `scale_with_distance`, `background`) and trail lines. megamap does no custom render
  pass and no GL calls.
- **Screens:** `screen_render_post` and the `screen_mouse_*`, `screen_key` and `screen_char` hooks on the mod's
  own screen. This is the world map: pan, zoom, cursor coordinates, the right-click menu, the waypoint list with
  search and filter, and the waypoint editor (name, colour, icon).
- **Options:** `settings` and `settings_click` add the megamap page to Options. `mods` lists the mod.
- **Keys:** the `key` hook, with `host.mod_key(ID, name, default)`. These are Horizon's key system, so players can
  rebind them in Options > Mods, and they are stored as `key.megamap.<name>`.
- **Commands and chat:** `commands`, `command` (`/megamap ...`), and `client_chat_received`, which spots shared
  waypoints for import and the death message.

### Keys (7) and the toolbar

Seven keys, under the limit of 9; everything else is in Options > Mods > megamap (35 rows) or the world-map
toolbar.

| name | default | action |
|---|---|---|
| map | M | open or close the world map |
| waypoint_here | B | waypoint at your feet, then the editor |
| waypoints | U | waypoint list (search and filter) |
| zoom | Z | minimap zoom: 0.5, 1, 2, 4 or 8 blocks per pixel |
| size | J | minimap size: 64, 96, 128 or 160 |
| mode | K | minimap mode: surface, cave or hidden |
| rotate | N | rotate with the player, or lock north |

World-map toolbar (top right, 16x16 icons with a tooltip on hover, text label if the icon sprite is missing):
zoom in, zoom out, centre on player, waypoint list, cave layer, trail, cloud fog, relief (cycles Flat / Soft /
Normal / Strong), grid (cycles Off / Chunks / Regions / Both). An active toggle gets an accent frame and underline.

## Waypoints

- `engine/waypoints.rs` keeps one list per world, with each waypoint tagged by its dimension. The list is saved as
  escaped tab-separated lines in `<data_dir>/<world key>/waypoints.txt`, so a hand edit or a newer field never breaks loading.
- Each waypoint has a name, a colour (8-entry palette), an icon (diamond, star, home, skull, flag or cross), a
  position, a dimension, and hidden or death flags.
- **Shown on** the minimap (clamped to the edge when off-map), the world map (with a hover tooltip) and in the
  world (a beam plus a "name (123 m)" label).
- **Death waypoint.** When the death screen opens, a death waypoint "Death day N" is added where the player died.
  It keeps the last `max_deaths` and drops older ones.
- **Sharing.**
  - `/megamap wp share <name>` sends `[megamap] name @ x y z (dim)` to chat (`send_chat`).
  - The world-map menu's "Share position" and "Coordinates to chat" prefill the chat box instead, because the API
    has no clipboard.
  - When another player's share arrives in chat, `client_chat_received` remembers it, and `/megamap wp import`
    adds it.
- **Commands.** `/megamap wp add [name]`, `wp del <name>`, `wp share <name>`, `wp list`, `wp import`,
  `trail clear`.

## LOD data beyond the loaded chunks

The map shows far terrain past the explored area from data Horizon already has on disk or in memory. It never
loads or generates a chunk on a server. Far tiles are a third map layer (`far`, id 2) saved in their own folder
next to the map, `<world>/<dimension>_far/r.X.Z.mmr`, so a second visit starts with them. `view` draws them
under the explored regions, so real map detail replaces them as you explore. Option: "Far terrain (LOD data)",
on by default. Cave mode never shows them.

**Why v0.2.0 showed almost nothing (causes).**

1. `sampler_ok` was false whenever the game's own LOD rendering was on, so the far thread had no source at all
   in the usual setup; only the live tiles were left.
2. `pick_far` ran once per world entry and never again: on a server the `server-terrain` folder appears only
   after the game's far terrain sees a chunk, so a first look found nothing and kept nothing.
3. The thread walked a fixed spiral of radius 40 chunks; the live tiles gave 4 chunks a frame on the game thread
   (about 240 chunks/s at 60 FPS, 0.5 regions/s); nothing was saved, so every session started from zero.
4. Single player sampled the generator 64 times a chunk even where the save already had the chunk.

**Sources now (`pick_far`, retried every 3 s while no far thread runs).** All work whether or not the game's LOD
rendering (`lodDistance`) is on:

1. **Server terrain** (servers): Horizon keeps the chunks it received in `server-terrain/<address>/.../r.X.Z.mca`;
   the far thread lists present chunks from the region headers (`far::read_mca_present`) and reads each chunk's
   columns through Horizon's public `server_terrain::ServerTerrain::chunk` (full surface: block, water, biome).
   Not for split-screen guests or friend sessions.
2. **The far disk cache** (`horizon_far_terrain`, `engine/hlod.rs`, zlib records) and **the save's region
   files** through the level's LOD source, a whole chunk at once (`request_detail`) or, while the game's LOD is
   on, column by column from the sampler's chunk cache (single player).
3. **The integrated server's LOD source** (single player): a coarse pass of the generator (one column every
   8 blocks, groups of 4x4 chunks) only where 1 and 2 have nothing, and only while the game's LOD is off.
4. **The live LOD tiles** (`game.lod`), on the game thread within 1.5 ms a frame, every 2 blocks.

**Planning.** Each pass reads the region headers around the open map's centre (or the player), up to 160 chunks
when the map is open and 48 for the minimap, lists every present chunk not on the map yet (`store::explored_mask`
of the map and far folders), sorts nearest first (`far::sort_tasks`) and bakes them in batches of 32; when the
view moves by more than a quarter of the radius it plans again. Batches carry an epoch; leaving the world or the
dimension bumps it and stale batches are dropped. The game thread integrates batches within 3 ms a frame.
The evict race of v0.2.0 (a region evicted while its load was in flight came back stale) is fixed: eviction
skips regions in `pending_load`, and a load result is dropped when its epoch is stale.

**Benchmark** (a release harness built against the real `server_terrain` reader, over a copy of the spm
overworld server terrain: 184 regions, 85473 chunks):

| path | time | chunks/s | regions/s |
|---|---|---|---|
| v0.3.0 far thread (mca read + bake) | 13.8 s | 6182 | 13.3 |
| v0.2.0 path, CPU only (64 samples a chunk) | 55.0 s | 1554 | 3.3 |
| v0.2.0 live tiles, frame-capped (4 chunks/frame at 60 FPS) | - | 240 | 0.5 |

**v0.3.1: phases and parallel readers.** The far thread now hands each block of 96 planned tasks to 1 to 3
readers at once (`far_part`, setting "Far LOD readers", auto = a quarter of the cores, at most 3). Each reader
has its own open files (`FarReaders`: its own `ServerTerrain`, `.hlod` handles), so they share no lock; chunks
only the save has go to the first reader (one generator sampler). Order is unchanged: nearest the open map's
centre (or the player) first, so the visible area fills before the rest; the view moving by a quarter of the
radius replans. The log line every 10 s gives regions/s, readers and read+decode / bake microseconds per chunk.

Phase split on the same spm copy (`mm_far_bench`, single thread, warm page cache, microseconds per chunk):

| read (record bytes) | decode (inflate + NBT; Horizon's summary is inside) | sample | bake | write (region encode + file) |
|---|---|---|---|---|
| 56.4 | 99.4 | 0.5 | 3.1 | 7.8 |

End to end (read, decode, sample, bake, region write), 85473 chunks:

| readers | time | chunks/s | regions/s |
|---|---|---|---|
| v0.3.0 read only (table above) | 13.8 s | 6182 | 13.3 |
| 1, full pipeline | 17.8 s | 4816 | 10.4 |
| 4, full pipeline | 6.1 s | 14099 | 30.4 |

The cost is reading and decoding Horizon's records; baking is 2 % of it. The game thread still takes at most
3 ms a frame to put batches into the far layer, which is not the limit at these rates.

**Not done: a cave layer for far terrain.** megamap's far readers keep only the surface of each column (height,
block, water, biome). The sources hold more (corrected in 0.3.4, see "Cave LOD" there), but a far cave layer is
not implemented; the setting slot planned for it is the reader count above.

**Server.** On a server only what Horizon already stored in `server-terrain` (chunks the game received this or
an earlier session) and the live tiles can show; nothing is requested from the server, so an area never visited
stays empty no matter how fast the readers are.

**The patch (optional, live tiles only).** `patches/far-surface-accessor.patch` adds one function to
`crates/horizon-client-render/src/lod.rs`: `Lod::megamap_surface(x, z) -> Option<Surface>`, the same lookup as
`ground()` returning the whole `Surface` (height, block, water face, biome). It reads only ready tiles. To use
it, on the RT stage after `horizon-mixins apply`:

```
patch -p1 < patches/far-surface-accessor.patch
RUSTFLAGS="--cfg megamap_far_source" cargo build ...
```

The mod switches with `#[cfg(megamap_far_source)]` (module `live` in `glue.rs`). The same `.hnmod` builds
either way. Without the patch the live tiles have no water and plains tints; sources 1 to 3 are complete either
way, so on a server the patch matters only for chunks the game has in memory but not yet on disk.

**Risks.** The `server-terrain` folder layout is Horizon's; if it moves, source 1 finds no files and only the
live tiles are left. The first `Integrated::call` per world entry blocks the game thread up to
the call timeout if the integrated server is busy.

## Entity faces and 3D previews (v0.3.1)

Code: `engine/portrait.rs` (pure: face crops, run merging, the CPU rasterizer, the player box model), the glue
section before `// Hooks.` (`Portraits`, `render_entity`, `mob_face`, `portraits_tick`, `draw_entity`,
`draw_entity_preview`).

**Why CPU.** The mod's only image is the one shared 1024² slot (see below), and native mods have no render
target or mesh hook. Faces and renders are drawn as merged runs of equal colour through `host.fill`, at most a few
hundred rectangles for a 96 px render.

**Faces (`ent_mode` = face).** Players: skin (8,8)-(16,16) with the hat (40,8) over it; legacy 64x32 skins work.
Mobs: the front face of the part named head (else the largest front-facing quad) read from the model's UV on the
mob's texture, hat layer over it; fewer than 24 opaque pixels falls back to an 8x8 front render of the model. A
1 or 2 px frame in the category colour (`face_frame`). Until a face is ready the plain dot is drawn.

**3D (`ent_mode` = 3D, and the preview in the entities window).** The mob's model posed by Horizon's own
`mobs::render::render_posed` into a vertex list (textures through a virtual atlas, the live texture of the
entity in place of the body one, the water mask layer skipped), then rasterized orthographically at a 3/4 view
(yaw -35, pitch 20) with 2x2 supersampling, a z-buffer, alpha cutout and Lambert light. Players use a box model
of the skin (steve / slim). Icons are 16 px, the preview is 96 px.

**Budget.** At most 2 texture decodes and 1 render a frame, only for what is on screen (blips in face/3D mode,
the rows of the entities window, the selected kind); caches of 512 faces, 256 renders, 256 textures. Measured in
the tests (release): 64 px front 0.37 ms, 116 px 3/4 1.19 ms per mob. A model or texture that cannot be used is
listed with its reason (no model, no geometry, no texture, empty); `MEGAMAP_PORTRAIT_BENCH=<file>` renders every
mob type once and writes the ms per mob and the failures.

## v0.3.2: auto layers, resource-pack colours, names, heads

**Auto layers** (`engine/layers.rs`, glue `probe_layer`, `cave_slice`, `layer_tag`). Mode Auto / Surface / Cave /
Fixed Y (setting and the toolbar layer button, which cycles the four). Each frame the glue builds one `Probe`:
the sky light at the feet (`host.light`) and the top of the player's column from the surface map already in
memory (no world read). `evidence` says surface, cave or unsure (rule: sky or height, sky only, height only);
`Detector` flips only when the evidence holds `ENTER_S` 1 s into a cave and `EXIT_S` 0.5 s out, so a tree, a
bridge or a short tunnel does not flip the map. The cave layer is a Xaero-style slice: the ceiling is cut at
`bucket_top(y)` (8-block steps, two blocks over the head) and the floor search stops `cave_depth` blocks under
it (`Layer::Cave(top, floor)` in the baker); the slice key `top * 64 + depth` is the cave layer's bucket, so a new
slice rebakes, and walking within the 8 blocks does not. A switch cross-fades the minimap for `FADE_S` 0.35 s
(`crossfade`, only during the fade). Cost per frame (bench): probe + slice 4.9 ns; cross-fade 0.11 ms for 0.35 s
after a switch; the slice bake runs on the worker (152 us a chunk), the cave minimap frame 1.2 ms like the surface
one.

**Resource-pack colours** (`engine/palette.rs`, glue `palette_upkeep`). Setting "Стиль цвета": vanilla map
colours, resource pack textures, auto (textures when any resource pack is on). There is no mod API for block
colours, so the glue (a child module of `game`, as all native mods are) reads Horizon's own client state:

- `game.settings.resource_packs: Vec<String>` and `game.settings.horizon.shader_pack: String` (empty: none);
- `game.native_block_sprites_version()`: bumps when the resources reload;
- `game.native_block_states() -> BlockStates`: `iter()`, `sprites(id) -> BlockSprites` (`sides[1]` is the top face,
  with its `TintSource`), `texture(SpriteRef) -> &str`;
- `game.native_client_resources() -> ClientResources`: `texture(name) -> TexturePixels { width, height, rgba }`.

On a change of `pack_hash(sprites version, pack list, shader pack, style)` a worker thread averages each state's
top texture (alpha weighted, first frame of a strip, cached by texture name: 2400 textures for 24000 states in
2 ms), keeps the tint source (grass / foliage multiply by the biome colour in the baker as before; an untinted
texture of a vanilla-tinted block gets `MC_PLAIN`), and writes them over a copy of the vanilla table
(`override_table`, 0.17 ms). With a shader pack on a slight contrast and warmth lift is applied (`shader_tint`):
shader packs expose nothing to mods, the map only knows one is on. The new table replaces the old one and the
loaded chunks rebake; saved and far regions keep their colours until they are baked again. The cache is in memory,
keyed by the hash (a restart recomputes it in a few ms). Proposal for Horizon: `mod_api` calls for the block
top colour and the active pack list, so a mod does not depend on `Game` internals.

**Names** (`engine/lang.rs`, `assets/megamap/lang/{en_us,ru_ru}.json`). Entities, biomes and dimensions are named by
the game's translation (`horizon_client::lang`) when the map speaks the game's language (setting "Язык": as in
the game, English, Russian), else the built-in table, else a prettified id. The entities window searches the shown
name and the id (`lang::matches`, `entities::list_named`); names are cached per language.

**Heads.** The entities window rows, the detail view, the 3D preview fallback and the settings preview legend
(the kinds on the radar now) show the 8x8 head whatever the radar mode; the blip only until the head is cached.
`portraits_tick` asks for those heads within the same budget (2 decodes, 1 render a frame).

**Icon frames.** Off by default; 0 to 3 px in quarter steps (0.25, 0.5, 0.75, 1, 1.5, 2, 2.5, 3). The whole
pixels are opaque rings, the fraction an outer ring at that coverage (`style::frame_rings`), so thin frames read
anti-aliased. Old values (1 or 2 px) migrate to quarter units; 0.3.0 settings keep no frame.

**UI fixed** ("Интерфейс не зависит от времени суток/погоды", default on): the auto theme stays dark, the frame
never changes (`style::ui_light`, `frame_colors`; tested over a day of ticks and all weathers).

**Settings sliders.** Auto-zoom near / far and the icon frame are drawn as a track with a knob; a click on the
track picks the step (`settings::SLIDERS`, `slider_step`); near never passes far.

**Clouds on small images (preview).** The cloud reach cap and the feather scale with the image
(`clouds::reach_cap_px`: 0.22·m capped at m²/1500). Before, fixed 40 px / 4 node floors with the 1.4 edge overlap
covered the whole 116 px settings preview in clear weather ("there is only the frame"). A test keeps the middle
third over 70 % clear at 1, 2 and 8 px per block. (0.3.3 replaced the pixel edge floor with a reach in blocks, below.)

**Cave LOD: not done.** The cave layer shows the loaded and saved chunks only. (The claim that was here, "the LOD
data is a surface heightmap with nothing under it", was wrong; 0.3.4 corrects it below.)

## v0.3.3: pan-stable fog, cloud reach in blocks, fog cost

**Pan-stable fog.** The cloud grid is anchored to the world, with `EXTRA` = 6 nodes beyond the visible lattice
on every side, so the light march and the edge shape near the image border see real neighbours: a node looks the
same wherever the pan puts it (test: pan invariance). The outer `SKIP` = 4 rings are never shaded and are cropped
before the refine.

**Cloud reach in blocks.** How far the clouds may lie over explored ground is a hard limit in world blocks:
"Заход облаков на карте" and "Заход облаков на миникарте" (separate values, 0 to 64 blocks, default 10), and
"Единицы захода: блоки/чанки". The value is always stored in blocks (`cloud_reach_blocks`, `mini_reach_blocks`,
`reach_chunks` in `settings.txt`). In chunk mode the slider and clicks step by 16 and the limit is rounded down to
whole chunks (`reach_blocks`: 23 -> 16), so the chunk mode only aligns, never widens. In pixels the limit is
`reach / blocks_per_px` (constant in the world at any zoom), capped by `reach_cap_px` on small images.

- Mask (`reach_mask`): an exact Euclidean distance (squared, u16) from every pixel to the nearest unexplored pixel
  (or margin node outside the image), up to `m = ceil(rpx) + 1`: a horizontal pass per row with run skipping, then
  a vertical min over the band. One `thread::scope`, bands of rows with their own halo, pooled buffers. Output: 255
  on unexplored, 0 at or beyond `rpx`, a smoothstep over the last `0.5·rpx` (the feather lies inside the limit).
  The composite and `mask_at` multiply the cloud density by it; the edge feather is `rpx / (1.4·cell)` nodes.
- Test `clouds_reach_hard_limit_in_blocks`: 9 cases (0.25 to 4 blocks a pixel, quality 0 to 3, rotation, round
  128 px minimap, reach 0 / 8 / 10 / 16 / 32 / 64); a brute-force distance to the unexplored pixels; beyond N blocks
  `mask_at` <= 1/255 and the output equals the plain map; near the border the clouds are there when N/bpp >= 4.
- Migration: 0.3.2 kept `cloud_reach` as an index of 3, 4, 6, 1, 2 (x0.47 nodes of overlap plus pixel floors).
  It becomes `round(c·10/3)` blocks (3 -> 10, 1 -> 3, 2 -> 7, 4 -> 13, 6 -> 20) for both maps, unless a
  `cloud_reach_blocks` line is present (test `settings_reach_blocks_chunks_migrate`).
- Look: at 2 blocks a pixel the default 10 blocks is 5 px, so the edge is almost crisp; at 0.5 a 20 px soft band.
  The settings preview shows the value of the tab (map or minimap).
- Cost (`examples/stage.rs`, 1024x576): margin + mask 0.6 ms at 10 blocks, 1.6 to 1.7 ms at 64; whole frame
  (abdump, medians of 12 x 10 frames, two rounds) q0 5.1 -> 5.2-5.3 ms, q1 9.9-10.1 -> 9.8-10.4, q2 16.9-17.3 ->
  15.1-16.8, q3 18.6-19.2 -> 18.0-18.4 (the wider overlap is gone, so fewer cloud pixels), minimap 256 1.5-1.7 -> 1.6.

**Fog cost (A/B).** `examples/abdump.rs` writes raw frames of 23 scenes (5 zooms, 4 qualities, day / sunset /
night / rain / storm / Nether / End, round 256 minimap) and median timings; the same file builds against an older
engine copy; a script compares max / mean diff, PSNR and 8x8 SSIM.

- Applied: `chamfer` and `box_blur` row-parallel (running sums in the same order, so the same additions), the
  `SKIP` rings left unshaded and cropped before the refine. Against the same code without them (1024x576, medians
  of 12): q0 4.69 -> 4.38 ms, q1 9.43 -> 8.93, q2 16.3 -> 15.0, q3 17.8 -> 16.6, minimap 1.65 -> 1.47; frames
  bit-identical in 15 of 23 scenes, the rest max 1/255 on <= 0.002 % of pixels (PSNR >= 99 dB, SSIM 1.0000).
- Rejected: a per-row `Vec` in the composite (q0 +0.4 ms); in the reach mask a u128 search for the alpha runs and
  run skipping in the vertical pass (no gain within the noise). The pan fix (wider grid) cost 0.3 to 2 ms against 0.3.2
  (q0 4.4 -> 4.7, q3 15.7 -> 17.8 ms); after the above it is 0 to 1 ms over 0.3.2 (q0 4.4, q3 16.6 against 15.7).

**Rectangular patches in the fog (user report, 4 blocks a pixel).** Next to the explored area the fog had
straight-edged rectangles of another density. Cause: far (estimated) terrain is drawn opaque, so the cloud pass
took it for explored ground. Far tiles come in chunk and region squares, so the fog thinned over them (deck
overlap, then 0.3.3's reach mask), and the far colours (grey: `Lod::ground` has no water) showed in squares under
a half-transparent deck. The cloud density itself was already a function of the world point, time and the explored
mask only (noise from `node_world` of global node indices, no per-tile seed or normalisation; the distance field
and its blur run over a domain `dm` nodes past the image, filled from the last frame or clamped copies).
Fix: with `mark_unknown` (cloud fog on) `view::render` gives far pixels alpha `FAR_ALPHA` (128), and the cloud
pass counts every pixel with alpha below 255 as not seen. Far terrain therefore lies under the fog like unknown
ground; with the fog off it is drawn as before. Test `clouds_far_terrain_hidden_and_tiling_invariant`: (1) the
same scene with the far squares marked FAR_ALPHA or plain unknown composites to within 1/255 (measured 0); (2) the
image rendered whole and stitched from 2x2 and 3x2 tiles, each rendered by a fresh engine with a 96 px halo,
agree away from the outer image border (worst 0 to 3/255, mean <= 0.0015) at 1 to 4 blocks a pixel, q1 to q3 and
a rotated view. Without the fix part (1) fails with 184/255.

### The 1024² mod image limit

Horizon gives a mod one 1024x1024 image (`MOD_IMAGE_SPRITE`). Workarounds, all in `glue.rs`:

- the minimap and world map share it (only one is visible at a time; the slot switches and re-uploads);
- a world map larger than 1024 GUI pixels is composed at a lower resolution and the sprite scales it up (at most
  2x); the GUI scale makes this rarely visible;
- uploads happen only when the view key changes, or on a cloud tick.

A real fix needs a second slot or a size query in Horizon; documented as an API gap, not patched.

## New features (3 plus 2 small)

1. **Breadcrumb trail** (`engine/trail.rs`).
   - What: a point every 4 blocks, up to 4000, kept per dimension and saved. It is drawn on both maps and as faint
     in-world lines nearby.
   - Why: with the death waypoint it answers "how did I get here" in caves and featureless biomes, where a
     waypoint alone gives a direction but not a safe path.
2. **Exploration fog and explored %.**
   - What: the region files already keep which chunks were explored. The world map can shade unexplored chunks
     (`fog`) and its status line shows the explored % of the view.
   - Why: it adds no storage cost and turns the map into a planning tool ("what haven't I seen near spawn?").
3. **Threat radar** (`engine/radar.rs`).
   - What: hostile mobs from the client's own entity list, shown as red blips on the minimap plus a count line.
     The optional passive-mob mode shows them in another colour.
   - Why: it is the most common reason players glance at a minimap at night. It reveals only what the client
     already tracks.
4. **Bonus: cave slice.** The cave mode bakes a horizontal slice around the player's y instead of the top surface,
   in its own layer and epoch, so switching modes is instant.
5. **Bonus: chat waypoint import.** One command adds a waypoint someone else shared.

## v0.3.4: far cave data (proposal, not implemented)

**What Horizon's far data holds.** `horizon_client_render::lod::Column` is `{ surface, spans }`: `spans` lists the
half-open material runs of the column (`Span { min, max, state, biome, light }`), and the gaps between runs are
air. Only kept blocks make runs (solid full-collision blocks, leaves, fluids, nearly full blocks), so torches,
rails and grass leave gaps, and a uniform section is one 16-block step. `Column::from_chunk` builds the spans from
every section, so a level-0 column has the caves exactly. Three places carry such columns:

- `.hlod` records (server-terrain cache): the payload stores the spans; `engine/hlod.rs::parse` reads only the
  surface today;
- `ServerTerrain::chunk(x, z)` and the sampler's `drain_details`: whole `[Column; 256]` per chunk;
- the live LOD tiles (`Lod.ready`): private, and `Lod::ground` exposes the surface only.

So a far cave slice needs no Horizon change for the saved data: parse the spans in `hlod::parse`, and bake a
cave slice from them with the same rule the near cave layer uses (topmost air gap under the slice top with a
floor). Coarser levels (`Column::reduced`) merge a footprint and fill caves, so only level 0 is usable.

**The patch (optional, live tiles only).** `patches/far-cave-sections.patch` adds `Lod::megamap_column(x, z) ->
Option<&Column>` after `ground`: the level-0 column at a block, `None` where only coarser tiles exist. It reads
tiles already sampled, never loads a chunk. It is not applied in the RT tree; it compiles there
(`cargo check -p horizon-client` with the patch staged) and stacks with `far-surface-accessor.patch` (fuzz 1).

**Not done in 0.3.4:** the span parse in `hlod::parse`, the cave bake from spans, and the use of the accessor.
Cost to watch: spans make a record several times larger to decode than the surface alone.

## Optimization pass (0.3.5)

A measured pass over the per-frame paths. Every change is bit-exact: 1256 renders and cloud frames (sizes,
zooms, rotations, smooth/mark/round, cloud looks, frame sequences) hash the same before and after, the tiling and
fog tests pass, and each change has its own test in `engine-tests/tests/opt_*.rs`. Times are medians of 10
interleaved rounds x 11 runs (base and patched binaries alternating, pinned to 6 cores) of a scratch bench; the
game was running beside it, so read them as relative. No in-game frame times were taken.

| change | where | measured |
|---|---|---|
| `Region::copy_pixels` allocates no mips (`ensure_mips` builds them if a copy is ever drawn) | `region.rs` | copy 0.62 -> 0.08 ms per dirty region save |
| `Clouds::composite` drops its final opacity pass (the row paths already write alpha 255) | `clouds.rs` | composite -1..-6 % |
| Box blur and the noise field on the calling thread (memory-bound, short: thread spawns cost more) | `clouds.rs` | dist stage -38 %, field -35..-48 % at 512 / q3 |
| Composite rows threaded from 64 K pixels (was 200 K), reach mask from 16 K (was 64 K) | `clouds.rs` | 192 px minimap: update 1.09 -> 0.84 ms, composite 0.84 -> 0.39 ms |
| `mask_round` (round minimap) clears the two ends of each row instead of testing every pixel | `glue.rs` | 192 px: 51 -> 14 us |

Together, on the default minimap (96 GUI px = 192 image px, clouds on): the cloud frame (update + composite)
went from about 1.9 ms to 1.2 ms on the main thread.

**Looked at and left alone:**

- The far thread re-reads region headers while idle. That is about 0.4 ms of I/O a second (363 header reads),
  so it is not worth a cache.
- A hash for `TexLoader`: textures are looked up once per block and only when zoomed in, so it would save at
  most about 0.1 ms.
- The `view::render` pixel loop dominates the minimap render (about 1.35 of 1.6 ms at 192 px; lighting is
  about 0.3 ms). A texel cache kept between renders would save at most about 20 %. It is not bit-safe either:
  the reveal changes with time, and night and generation change too.

**Proposals (need a design decision or a Horizon change):**

- Thread `view::render` by rows. This needs `Lookup: Sync`, so `TexLoader::want` must become a `Mutex` or a
  per-band list.
- Shift the previous minimap image instead of rendering it again every frame while walking (the key moves by
  1/8 px).
- A persistent worker pool instead of `thread::scope` spawns per pass.
- Upload only part of the mod image (Horizon API).

## Optimization pass (0.3.9): the far-zoomed map

Measured with `engine-tests/examples/farbench.rs`: a 1024 x 576 world map panned 7 px a frame over a store of
5 x 5 explored and 11 x 11 far regions, clouds on (quality 1, the cloud time held four frames as the glue holds
it during a drag), default settings. Medians, the game running beside the bench (read them as relative). Every
image change below is bit-exact: `engine-tests/src/golden.rs` hashes 360 map frames and their cloud frames (three
places, ten zooms, smooth / marked / turned / round / grid / reveal / coarse far) and `golden_frames_unchanged`
holds the hash taken from the 0.3.8 code.

| blocks a pixel | map render 0.3.8 -> 0.3.9 | whole frame 0.3.8 -> 0.3.9 |
|---|---|---|
| 2 | 9.1 -> 8.1 ms | 9.8 -> 8.9 ms |
| 8 | 10.6 -> 7.5 ms | 18.4 -> 12.4 ms |
| 16 | 8.2 -> 3.0 ms | 20.0 -> 9.7 ms |
| 32 | 11.0 -> 2.3 ms | 23.2 -> 9.4 ms |
| 64 | 9.4 -> 1.1 ms | 21.8 -> 8.4 ms |

What changed:

- **Empty spans** (`view::render_rows`). A far-zoomed map is mostly ground no region knows, and every such
  pixel paid the full sampling (four texels, the filter, the float blend), about as much as a known one. In an
  unturned view a row runs along world x: where neither store has a region under a pixel's texels the pixel is
  the unknown fill, written directly up to the region's last texel column; a row outside the lookup's bounds is
  one fill.
- **Region table** (`view::Grid`). The regions under the image are looked up once a render (the image's region
  rectangle cut to `Lookup::bounds`, which the glue answers from its two stores) instead of through one-region
  caches in front of two hash maps: at 64 blocks a pixel a row crossed a region every 8 px and asked the maps
  about twelve times for each.
- **`Lookup::has_coarse_far`**: the glue has no coarse far terrain, so the unknown fill does not ask `far` per
  pixel.
- **`floor` without libm** (`view::ffloor`, `clouds::ffloor`): the game is built for baseline x86-64, where
  `f64::floor` is a library call; the map took four a pixel, the cloud grain and noise several a sample.
- **Cloud composite**: the node refine runs by output row on the cloud threads and no longer zero-fills its
  3.6 MB of scratch a frame (0.8 -> 0.2 ms); the grain tile is addressed with masks. Composite 5.9 -> 4.2 ms.
  The cloud threads are half the cores like the map's (four where there are four).
- **`Store::plan`**: the regions to keep loaded are picked from rings around the view centre, not by listing,
  copying and sorting every region the view touches (32 000 at 64 blocks a pixel: 0.25 ms a frame, 0.9 ms at
  the far end). `Store::shown` is the rectangle.
- **Mips of a read region on the worker** (`Job::Load`), not on the game thread (1.3 ms a region; a far-zoomed
  pan takes in a dozen a frame).
- **`settle_revealing`** only while a reveal front runs (it walked every pixel of every map frame).

Game-thread costs outside the image (not in the bench, not measured in game):

- **Live far tiles** (`far_upkeep`): a pass over the 193 x 193 chunks around the player asked `Lod::ground` for
  64 columns of every chunk the game has no tile for, every pass, within 1.5 ms a frame: with far terrain on and
  the game drawing its own, that budget was spent on nearly every frame. Now five columns (middle and corners)
  decide whether a chunk has a tile at all, and a pass that baked nothing is followed by a one second pause.
- **Trail on the world map**: one HUD rectangle per trail point on screen; zoomed out they fall on the same
  pixels, so a dot is drawn only once it is a pixel from the last one.

Looked at and left: a thread pool (a scope of five spawns measured 0.05 ms; six scopes a frame); shifting the
last frame on a pan (the image moves by fractions of a pixel and the clouds sit on top); the per-pixel cost of
the composite (4 ms of the 8.4 left at the far end) without changing its arithmetic.

## 0.3.11: far terrain and the fog, rooms, the entity preview

- **Fog keeps off loaded far terrain** (`Clouds::kfar`). The fill over far terrain was only bounded by the node
  grid: 9 to 25 px in from every bit of void, hundreds of blocks of loaded terrain on a zoomed-out map. Far
  pixels now get a per-pixel reach against the void like explored ground has against the unexplored
  (`lod_front_px`: 16 blocks, at least 4 px).
- **Far terrain streaming in** no longer drops the fog a chunk square at a time: every lattice node remembers
  that it was all void (`Clouds::voidv`) and lets go over `VOID_FADE_S` (0.8 s); the glue keeps cloud frames
  coming at 30 a second while that runs (`Clouds::easing`).
- **Far readers**: on automatic, half the cores (up to 6) while the world map is open, a quarter (up to 3) behind
  the game as before.
- **Textures on explored ground saved before 0.3.5** (no block ids): the far thread bakes those chunks too, and
  `region::saved_block` takes the far column's block where it is the same surface (the same height).
- **Layer probe** every 150 ms on its own clock (it came with the chunk snapshot, twice a second); the room view
  comes in after 0.25 s and goes after 1.2 s. A jump (up to two blocks, back within a second) is probed from
  the floor it started on.
- **Entity preview**: a fixed frame (the model's bounding sphere, `portrait::raster_fit`) instead of a refit to
  the turned outline every frame, and the wheel zooms it (0.6x to 4x).
- **Far layer in the palette in use** (`far_palette_sync`): the far folder remembers the palette it was baked
  with (resource packs, shader pack, colour style, without the session's resources generation); under another
  one its region files and memory are dropped and the far thread, restarted with the new table, bakes them
  again. The far thread starts only once the pack palette is in.
- **Interface**: settings groups fold (a click on the header; folded shows the item count); a right click on a
  waypoint, on the map or in the list, opens its own menu (edit, hide / show, find, send to chat, teleport,
  delete), the map's menu gained "teleport here"; the waypoint dialog shows all colours and icons to pick with
  one click and a checkbox instead of rows that cycled on click; the list button is a map pin, the trail button
  steps with an arrow head.
